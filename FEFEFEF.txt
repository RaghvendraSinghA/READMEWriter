What is a token ?
A token is a chunk of text, roughly 3 to 4 characters of English, or about three-quarters of a word.

e.g.—> 
"cat"      → 1 token
"hello"    → 1 token
"the"      → 1 token

"unbelievable"   → un | believ | able         (about 3 tokens)
"tokenization"   → token | ization            (about 2 tokens)
"Bengaluru"      → Beng | al | uru            (about 3 tokens)

"Hello, world!"  → Hello | , | world | !      (about 4 tokens)

The space before a word is usually attached to the word, so “  world” is a single token.

"2026"           → about 1 to 2 tokens
"print('hi')"    → print | (' | hi | ') | ...  (about 4 to 5 tokens)


 Rough sizes:
* 1 million tokens is about 750,000 words, or several long novels, or a large codebase.
* 128,000 tokens is about 96,000 words, or a short book.

Newer models use a token-izer that produces about 30% more tokens for the same text than older ones like Haiku 4.5, so the same document uses more of the window.

Hindi, Kannada and other non-Latin scripts usually use more tokens per word than English.


Summary:

* 1 token is about 4 characters, or about ¾ of a word.
* 100 tokens is about 75 words.
* A page of text is about 400 to 500 tokens.



What is claude 400 error ?

A 400 from the Claude API means invalid_request_error: the server understood the request but rejected it because something in it is malformed or not allowed. It’s a problem with the request, so retrying the same request will fail the same way.
The error body looks like this:

json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "max_tokens: Field required"
  }
}
The message field tells you what’s wrong, so read it first.

Common causes

* Missing or wrong fields: no max_tokens, no model, or an empty messages list.
* Bad message structure: roles that don’t alternate properly, the first message not being from the user, or an empty content block.

The first message not being from the user
The conversation must start with a user message. Starting with assistant is rejected:

json
"messages": [
  {"role": "assistant", "content": "Hello!"},   // wrong first message
  {"role": "user", "content": "Hi"}
]
This often happens when you load saved chat history and the first user turn got trimmed off.

An empty content block
Every message needs real content. These cause errors:

json
{"role": "user", "content": ""}
{"role": "user", "content": []}
{"role": "user", "content": [{"type": "text", "text": ""}]}
This usually comes from code that sends a blank string, such as an empty text box or a failed earlier step that returned nothing.


* Invalid JSON: a stray comma, bad escaping, or a wrong content type.
* Unsupported parameters for that model: the newer models (Sonnet 5 and later) return 400 if you set temperature, top_p or top_k to non-default values, or use manual extended thinking budgets. This is the most likely cause if you’re moving older code to Claude 5.x.
* Thinking settings: max_tokens too small for the thinking setup, or a bad thinking configuration.
* Bad tool definitions: malformed JSON schema, or a tool_result that doesn’t match a tool_use ID.
* Invalid content: unsupported image type, an oversized file, or a bad base64 string.
* Too much input: a prompt that exceeds the context window.
* Billing: some account or credit problems also come back as invalid_request_error, such as a credit balance that’s too low.


How to debug it
1. Read error.message and fix the field it names.
2. Check the model’s page in the docs for parameters it no longer accepts.
3. Strip the request down to a minimal one (model, max_tokens, one user message), then add pieces back until it breaks.


Related errors
* 401: bad or missing API key.
* 403: your key isn’t allowed to do that.
* 404: wrong model ID or endpoint.
* 413: request too large.
* 429: rate limited.
* 500 and 529: server errors or overload, where retrying is appropriate.
The full list is in the API errors page at docs.claude.com. If you paste the exact error message and your request (with the key removed), I can tell you what to fix.


CONTEXT WINDOW and MAXIMUM OUTPUT :
These are the two size limits that apply to every request to a model like Sonnet 5.5, Opus 5.5 or Haiku 5.5.

Context window: 1 million tokens
This is the model’s working memory for a single request:
 the most text it can see at once. Everything counts toward it:
* Your system prompt
* The whole conversation history you send in messages
* Files, images and documents you include
* Tool definitions and tool results
* The model’s own thinking and reply
If the total goes past the limit, the request fails (or gets cut off), and the model can’t see anything beyond it. 

Maximum output: 128,000 tokens
This is the longest single reply the model can produce in one response. It’s separate from the context window, and it’s much smaller. Your max_tokens setting caps the reply at or below this number. With thinking enabled, thinking tokens count toward max_tokens, so a low value can cut the response off after the thinking and before any answer text.

Token calculation on prompt and result from request and response of claude API.

- input (prompt + history + files) + output (thinking + reply) ≤ 1M tokens.

- reply (including thinking) ≤ 128K tokens




ADAPTIVE VS EXTENDED THINKING

Extended thinking — older configuration

You explicitly enable thinking and set a token budget.
thinking = {    "type": "enabled",    "budget_tokens": 10000}

Used by models such as Haiku 4.5 and Opus 4.5. Some intermediate models deprecated this configuration.

Adaptive thinking — newer configuration
The model decides whether and how deeply to think for each request. You steer its behavior using effort.
thinking = {    "type": "adaptive"}output_config = {    "effort": "high"}

Used by newer models such as Fable 5.1, Opus 5.5, Sonnet 5.5, and Haiku 5.5. Exact configuration options vary by model.


With a fixed manual budget, the older configuration allocates a specific maximum number of tokens for thinking. With adaptive thinking, Claude decides how much thinking is appropriate, while effort influences its overall reasoning behavior.


Effort levels explained
Level	Meaning	Example use
low	Minimize effort, latency, and token use	Simple classification
medium	Balanced reasoning and cost	Routine coding tasks
high	Deeper reasoning for harder work	Debugging a complicated Django bug
xhigh	Extended capability for demanding tasks	Long-running agentic coding
max	Maximum capability with no effort constraint	Extremely difficult, high-stakes engineering analysis


These levels are not fixed token budgets. A high request does not guarantee a particular number of thinking tokens. Support also varies by model: for example, Opus 4.6 supports max but not xhigh, whereas Opus 4.7 supports both.

Higher effort generally encourages more thorough reasoning, potentially increasing latency and token usage. However, it still does not mean that Claude must consume the maximum possible tokens.

Effort is Directly propotional to Thinking propotional to cost.



What are sampling parameters?
Sampling parameters influence how a language model chooses the next token when generating a response.

The three parameters are :

temperature
Controls the randomness of token selection.
* Lower values generally produce more predictable output.
* Higher values generally produce more varied output.
* It does not directly control the amount of reasoning. 
top_p
Uses nucleus sampling: it considers a group of likely tokens whose cumulative probability reaches a specified threshold.
For example, top_p = 0.9 selects from a probability-based candidate set containing approximately 90% of the probability mass.


top_k
Restricts sampling to the k most likely next-token candidates.
For example, top_k = 10 limits the candidate set to the 10 highest-probability tokens.
These are general sampling concepts. The exact supported behavior depends on the model and API

Prompting guides the model's behaviour, but it is not a mathematically equivalent replacement for sampling controls.

Why You Need a Server ?

You should never make requests to the Anthropic API directly from client-side code. Here's why:
* API requests require a secret API key for authentication
* Exposing this key in client code creates a serious security vulnerability
* Anyone could extract the key and make unauthorized requests
Instead, your web or mobile app sends requests to your own server, which then communicates with the Anthropic API using the securely stored key.

RAG
Retrieval Augmented Generation (RAG) is a technique that helps you work with large documents that are too big to fit into a single prompt. Instead of cramming everything into one massive prompt, RAG breaks documents into chunks and only includes the most relevant pieces when answering questions.


RAG pipeline:

Chunking:
Size based chunking—>

	Size-based chunking is the simplest approach - you divide your text into strings of equal length. If you have a 325-character document, you might split it 	into three chunks of roughly 108 characters each.


Structure based chunking—>
	Structure-based chunking divides text based on the document's natural structure - headers, paragraphs, and sections. This works great when you have well-formatted documents like Markdown files.

Semantic based chunking (sentence or section)—>
	A practical middle ground is chunking by sentences. You split the text into individual sentences using regular expressions, then group them into chunks with optional overlap: like sentence breaking.

Choosing Your Strategy
Your choice depends entirely on your use case and document guarantees:
* Structure-based: Best results when you control document formatting (like internal company reports)
* Sentence-based: Good middle ground for most text documents
* Size-based: Most reliable fallback that works with any content type, including code
Size-based chunking with overlap is often the go-to choice in production because it's simple, reliable, and works with any document type. While it may not give perfect results, it consistently produces reasonable chunks that won't break your pipeline.

RAG FLow—>

Chunking —> Embedding (gives magnitude of each word related to topic -1 to 1) —> normalization (adjusting magnitude of embeddings to 0-1) —> store chunks and their magnitudes —> user queries ( then do chunking —> normalization  on his query) —> search on vector database (which internally uses cosine simillarity) and return the answer.

	Corrected RAG flow
1. Chunking (indexing time): Split your documents into passages, usually 200-500 tokens, often with some overlap so context isn’t cut mid-thought.
2. Embedding: An embedding model turns each chunk into a single vector (hundreds or thousands of dimensions). It isn’t a magnitude per word relating to a topic. Each dimension has no human-readable meaning on its own; the meaning lives in the vector’s overall direction. Values can be negative or positive, but they aren’t confined to -1 to 1 unless normalized.
3. Normalization: Scale each vector to unit length (L2 norm = 1). This doesn’t squash values into 0-1. Individual components can still be negative. What it does is make cosine similarity equal to a simple dot product. Many embedding models already return normalized vectors.
4. Store: Save the chunk text, its vector, and metadata (source, page, etc.) in a vector database.
5. Query time: The user’s question is embedded with the same model (not chunked, since it’s short) and normalized the same way.
6. Retrieval: The vector DB finds the top-k nearest chunks, usually via cosine similarity or dot product, often using an approximate index like HNSW for speed.
7. Generation (the missing step): The retrieved chunks are inserted into the LLM’s prompt along with the question, and the LLM writes the answer. The vector database only returns relevant chunks, not answers.

How does cosine similarity work?
Cosine similarity measures the angle between two vectors.
\[ \text{cosine similarity}= \frac{\mathbf{A}\cdot\mathbf{B}} {\|\mathbf{A}\|\|\mathbf{B}\|} \]
Its value ranges from -1 to 1 mathematically.

- Close to 1: vectors point in similar directions.
- Close to 0: vectors are approximately perpendicular.
- Close to -1: vectors point in opposite directions.

With Anthropic’s prompt caching, the "ephemeral" cache type lasts 5 minutes by default.
* Refreshed on use: Each time the cached prefix is read, the 5-minute timer resets at no extra cost. A prompt you hit at least every 5 minutes stays cached.
* 1-hour option: You can request a longer lifetime with "cache_control": {"type": "ephemeral", "ttl": "1h"}. Writing to the 1-hour cache costs more than the 5-minute one.
* Pricing: Cache reads are much cheaper than normal input tokens, and cache writes cost somewhat more than normal input.
* Exact match required: The cached prefix must be identical (tools, system prompt, and messages up to the breakpoint), or you get a cache miss.

* No internet access: Code runs in a sandboxed container with outbound network access disabled. It can’t call external APIs, download files, or pip install from the internet, so you’d pass in any data it needs through the Files API or the conversation.
